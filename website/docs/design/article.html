一次 Next.js 博客工程的取舍

从 Next.js 与 Vite 的组合实验，回到一个标准、稳定且更少意外的起点。 这不是对工具热情的否定，而是一次关于长期维护的选择。

N
Nubbi Filed under Engineering Notes

起点

为博客选择技术栈时，我最初对 Next.js + Vite 的组合产生了兴趣。Vite 的开发体验足够直接，而 Next.js 已经提供路由、服务端渲染、元数据和缓存等完整能力。把两者放在一起，听起来像是同时获得两边的优点。

但工程选择真正困难的部分，往往不在“能不能运行”，而在半年以后是否依然容易理解、升级和排查。 一个实验性的组合可能在第一天带来新鲜感，也可能在每一次框架更新时收取额外成本。

对个人项目来说，维护成本不是抽象指标。它最终会直接决定，我还有没有心情继续写作。

真正的取舍

我把选择拆成三个维度：今天的开发体验、未来的兼容风险，以及项目真正需要的能力。 当需求只是一个内容型博客时，标准 Next.js 已经覆盖了当前阶段的全部基础设施。

01 / NEED 实际需要

路由、渲染、元数据和可预测的生产构建。

02 / COST 额外成本

适配层、插件兼容和框架升级后的持续验证。

03 / CHOICE 最终选择

先使用标准 Next.js，把复杂度留给真实需求。

这并不意味着组合方案没有价值。它仍然是理解框架边界的好实验，只是不适合作为这个博客的默认基础。 技术探索可以继续存在，但不必让每一次探索都进入产品主线。

保留的结构

最终项目保留一套很薄的基础：App Router、TypeScript、Tailwind CSS， 以及独立的 workspace 边界。运行方式保持明确，不让根项目承担额外编排。 

pnpm --filter nubbi-website dev
pnpm --filter nubbi-website typecheck
pnpm --filter nubbi-website build

内容功能暂时后置

Markdown、API 客户端、文章数据模型和部署方式都没有在初始化阶段提前决定。 它们会在内容来源与发布流程明确以后再进入工程，而不是先安装一批“以后可能需要”的依赖。

写在最后

我越来越喜欢一种朴素的工程节奏：先让边界清楚，再让功能生长。 好的基础不一定展示最多能力，它只是让下一步足够自然，也让回头修改时不必付出太多勇气。

对“拾光笔记”来说，技术最终应该退到文字之后。读者看到的是文章、时间和思考， 而不是支撑它们的工具清单。
